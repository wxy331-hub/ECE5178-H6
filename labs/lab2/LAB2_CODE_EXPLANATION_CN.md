## 3. 状态、控制量与测量量

**状态** `x = [x, y, heading, speed]`，四维：位置（米）、航向（弧度）、速度（米/秒）。

**控制量** `u = [speed_cmd, heading_cmd]`：期望速度与期望航向角。注意第二项是**目标角度**，不是转向角速度。

**测量量** `z = [heading, speed]`，二维。位置**不在测量里**——这一点决定了滤波器的行为：位置只能靠模型推算，其不确定度只会增长，不会被观测收缩。这也是 Lab 3 需要引入位置观测的原因。

坐标约定沿用实验环境：

- 航向 `0` 指向 `+y`，`π/2` 指向 `+x`；
- 因此位置积分是 `x += v·sin(θ)·dt`、`y += v·cos(θ)·dt`；
- 反过来由位置误差求航向是 `atan2(误差x, 误差y)`，参数顺序与常见的 `atan2(y, x)` 相反。

## 4. 运动模型与参数标定

模型在 [`EKF.py`](./EKF.py) 的 `dynamics()`，方程与 Lab 1 提交的 `33377006_m1_2.py` **完全相同**，只有常数按实机重新标定过。作业同时要求「沿用 Lab 1 的运动模型」和「用真实机器人标定」，当某个 Lab 1 常数被测量否定时，这两条会冲突；处理方式是**方程不动、常数重估**，并由测试 `test_dynamics_equations_match_lab1_under_lab1_parameters` 把方程钉死（把 Lab 1 的参数喂进 Lab 2 的 `dynamics`，要求输出逐位相同）。

```python
MODEL_CONFIG = {
    "dt": 0.105,
    "max_speed_m_s": 0.50,
    "speed_gain": 1.957,
    "speed_time_constant_s": 0.216,
    "max_acceleration_m_s2": 1.79,
    "max_deceleration_m_s2": 1.33,
    "max_turn_rate_rad_s": 7.5,
    "command_deadband_m_s": 0.0537,
}
```

模型包含五个环节：

**① 转向率限制。** 每步航向变化被限制在 `max_turn_rate × dt` 内：

```python
heading_step = clip(heading_error, ±max_turn_rate·dt)
```

**② 命令死区。** 小于 `command_deadband` 的速度命令只让机器人原地晃动，不产生位移。模型用「减去」而不是「阈值置零」：

```python
effective = max(|speed_cmd| - deadband, 0)
desired  = sign(speed_cmd) · speed_gain · effective
```

减法形式在死区边界处连续（阈值置零会产生跳变），物理上也对应「先克服静摩擦，剩余功率才转化为速度」，而且几乎处处可微，对 EKF 的数值雅可比更友好。

**③ 一阶速度响应。** 电机达到目标速度需要时间：

```python
first_order = speed + (1 - exp(-dt/τ))·(desired - speed)
```

**④ 加减速率限制。** 加速与减速上限不同（1.79 / 1.33 m/s²），反映实机加速比刹车快。在本实验的命令范围内这一环节几乎不触发，它是为更大命令准备的保护。

**⑤ 中点积分。** 位置用中点航向与平均速度更新：

```python
heading_mid = heading + 0.5·heading_step
speed_mid   = 0.5·(speed + speed_new)
x_new = x + speed_mid·sin(heading_mid)·dt
```

转向与加速同时发生时，用起点状态积分会低估位移、用终点会高估，中点法是二阶精度。

### 参数的测量依据

| 参数 | 依据 |
| --- | --- |
| `speed_gain` = 1.957<br>`command_deadband` = 0.0537 | 二者是同一条直线 `v = k(u − u₀)` 的斜率与 x 截距，**单个工作点解不开两个未知数**。由实机两个工作点联立：raw 7 → 0.0318 m/s，raw 10 → 0.0905 m/s，两点都精确落在拟合线上。 |
| `max_turn_rate` = 7.5 rad/s | 陀螺仪实测：转弯峰值 511 °/s，两步积分得 87.6°，即机器人两步转完 90°。Lab 1 的 2.61 需要六步，导致实测航向长期领先预测。 |

## 5. EKF 预测

预测步把状态与协方差推进一个周期：

```text
x⁻ = f(x, u)
P⁻ = F·P·Fᵀ + Q
```

`f` 就是上面的 `dynamics`。`F` 是它的雅可比，用**中心差分数值求得**：

```python
F[:, j] = (f(x + εeⱼ, u) − f(x − εeⱼ, u)) / (2ε)
```

模型含限幅、死区、速率限制和角度归一化，写一个全局解析雅可比容易出错，而数值雅可比在常数被重新标定后依然正确。角度分量的差分要先归一化，避免 ±π 附近的跳变污染导数。

## 6. 测量模型与更新

测量模型是线性的：滤波器只观测航向和速度。

```python
h(x) = [wrap(heading), speed]
H = [[0, 0, 1, 0],
     [0, 0, 0, 1]]
```

更新步：

```text
ν = z − h(x⁻)          （航向分量先归一化到 [−π, π)）
S = H·P⁻·Hᵀ + R
K = P⁻·Hᵀ·S⁻¹
x = x⁻ + K·ν
```

卡尔曼增益用 `np.linalg.solve` 求解而不是显式求逆，数值上更稳。

### 6.1 测量量从哪来（本实验的核心）

**在仿真中**，观测是真值加高斯噪声，本身就是合法测量，直接使用。

**在实机上，观测向量里的航向和速度都不是测量值。** `api.get_speed()` 与 `api.get_heading()` 返回的是最近一次 `set_speed()` / `set_heading()` 写入的内部变量，也就是**把命令原样回显**。把它当测量喂给滤波器，等于让滤波器去追自己的输入：新息不再是零均值噪声，而是「命令与模型响应之差」这个恒定偏置。

实机改用两个真正的传感器：

**速度 —— 轮式编码器。** `robot_speed_measurement()` 从 `info["velocity"]` 取轮速：

```python
speed = hypot(vx, vy) / 100.0     # API 单位是 cm/s
```

只取模长：接口文档说明 `x`/`y` 是右/前方向，但没说明这是机体系还是世界系，取模在两种情况下相同；符号由命令决定，不存在歧义。若这一帧数据缺失则返回 `None`，退回观测值——丢包只会降低测量质量，不会注入 `NaN` 或让滤波器停摆。

**航向 —— IMU 偏航角。** `ImuHeadingSensor` 从 `info["orientation"]["yaw"]` 取姿态角（作业说明中列出的实机可用测量正包含陀螺仪）。这里有两个未知量：

- **零点被精确消除，不需要假设。** 不用 yaw 的绝对值，而是把第一帧记为参考，之后只用相对差值。IMU 原点在哪完全不影响结果。
- **符号必须假设，但猜错可检测可恢复。** `IMU_YAW_SIGN = -1.0`，由实机数据确定：把测得的 yaw 对指令航向做回归，斜率 −0.99（文档标称的顺时针为正在这台机器上不成立）。若符号猜错，测得航向会与指令**持续相差约 180°**；而正常转向瞬态最大 90°、六步内衰减。两者之间有干净的间隔，因此取 **120° 阈值、连续 10 步**作为判据：持续超限就打印警告、停用 IMU、回退到观测值。猜错的代价是一条警告，不是整次实验作废。

## 7. 协方差更新与数值稳定性

协方差用 **Joseph 形式**更新：

```python
P = (I − K·H)·P·(I − K·H)ᵀ + K·R·Kᵀ
```

比常见的 `P = (I − K·H)·P` 多一项，但在 `K` 不是严格最优增益时仍能保持对称正定——而 `Q`、`R` 是手工调出来的，`K` 本来就不严格最优。

每次预测与更新后再做一次强制稳定：

```python
P = 对称化(P) 后特征值截断到 ≥ 1e-12
```

防止长时间累积的浮点误差让 `P` 失去正定性（那会让评分要求的最小特征值检查失败）。

## 8. 噪声矩阵

初始协方差：机器人从已知原点启动，位置几乎确定，航向与速度略有不确定。

```python
P₀ = diag(1e-6, 1e-6, 6.25e-4, 6.25e-4)
```

仿真与实机使用**不同**的噪声矩阵——两者的噪声来源本就不同：

| | 仿真 | 实机 |
| --- | --- | --- |
| `Q` | `diag(3.125e-6, 3.125e-6, 1e-4, 2.5e-5)` | `REAL_PROCESS_NOISE = diag(3.125e-5, 3.125e-5, 3.0e-3, 2.5e-5)` |
| `R` | `diag(6.25e-4, 6.25e-4)` | `REAL_MEASUREMENT_NOISE = diag(1.03e-2, 1.08e-3)` |

**实机 `R` 的航向项比仿真大 16 倍**，因为它取自实测新息的方差：航向新息的标准差是 0.10 rad，而仿真假设 0.025。差距来自 IMU 读到的不只是传感器噪声，还包含机器人在不平地面上的真实偏摆。

**实机 `Q` 的航向项放大到 3e-3**，吸收同一来源的过程扰动。这个值不是随便放大的：用实机日志离线重放扫描过，`Q` 再往上加会让估计过度信任测量、跟着扰动跑，评分指标反而变差。

## 9. 轨迹：沿黄线走一圈

实验场地是一条圆角矩形赛道，中间有障碍。轨迹按黄线设计：

```python
TRACK_STRAIGHT_X = 0.385     # 长边直线段
TRACK_STRAIGHT_Y = 0.395     # 短边直线段
TRACK_RADIUS     = 0.065     # 圆角半径
TRACK_LAP        = 1.968     # 一圈周长（自动算出）
```

赛道被描述成八段「(弧长, 航向变化)」的序列，`track_heading(distance)` 查表返回该弧长处的切线方向：直线段航向不变，圆角段航向随弧长线性变化——这正是等半径匀速转弯的行为。

**为什么不走正方形。** 正方形在每个角要求一步之内转 90°，机器人会以 511 °/s 硬转，代价是前进速度几乎全部损失，随后需要约两步重新建立。实测中十次「几乎不动」的步里有八次落在这个窗口内——转弯后的低速期一旦压上地面高点就彻底推不动。而 0.065 m 圆角在 0.09 m/s 下只需要 1.39 rad/s，即**每步 8.4°，机器人能力是 45°/步**，可以边转边保持前进，低速窗口根本不出现。

### 9.1 按实测位移推进，而不是按时间

`scripted_action(travelled, initial_heading)` 的参数是**已经走过的距离**，不是 `step × speed × dt`。

两者在机器人卡住时会分道扬镳：早期版本用时钟推进，机器人顶在地面高点上不动时，调度仍在照常前进，结果转弯命令在真实位移只有 0.219 m 时就发出（直线段应为 0.32 m），提前 0.10 m 切进内侧撞上中央障碍。

改用实测位移后，**卡顿消耗时间但不消耗轨迹进度**，机器人恢复后从原地继续走那个圆角。位移来源：实机取 locator（卡住时它不动），仿真取自身真值，两个环境共用同一份进度。

单步位移还有一道限幅：

```python
travelled += min(moved, max_speed × dt)     # 上限 52 mm
```

locator 偶尔跳变——某次运行有四步报告 54–70 mm 而编码器只有 18–27 mm，任何机器人能达到的速度都解释不了。一帧坏数据若落在圆角里会跳过一段转弯，实测中 180° 与 270° 的到达点因此晚了 0.35 m。读数正常时这道限幅不起作用。

### 9.2 走满一圈即停

```python
completed = travelled >= TRACK_LAP
speed = 0.0 if completed else SCRIPT_SPEED
```

200 步能走多远取决于卡顿率——干净时约 1.1 圈，卡顿 37% 时只有 0.7 圈，**选任何速度都固定不了圈数**。所以直接从终点判断：走满一圈就停住。作业要的是 200 步**数据**，不是 200 步**行驶**；而且静止对滤波器不是浪费——那是它应当预测得最准的状态，实测静止段的 Mahalanobis 距离比运动段还小。

命令速度 `SCRIPT_SPEED = 0.12`（raw 12），比重估的死区 0.0537 高出 4.6 档，留足了不被地面高点卡住的余量。

## 10. 控制周期与蓝牙节流

`ThrottledRobot` 继承框架的 `Robot`，只覆盖一个方法：

```python
def set_heading_and_speed(self, heading_deg, speed):
    with self._lock:
        if int(heading_deg) != self._last_heading_deg:
            self.api.set_heading(int(heading_deg))
            self._last_heading_deg = int(heading_deg)
        self.api.set_speed(int(clip(speed, 0, 255)))
```

原因在底层接口：`set_heading()` 与 `set_speed()` 最终发出的是**同一条** `roll_start(heading, speed)` 命令，而 `set_heading()` 那条携带的是**上一次的速度**，一个完整蓝牙往返之后就被第二条覆盖。航向不变时这次写入毫无作用，而绝大多数步航向都不变。

去掉它之后，控制周期从 **209 ms 降到 104.9 ms**——这直接决定了 EKF 的正确性，因为 `EKF` 按 `dt` 预测位移，周期偏差一倍就意味着预测位移错一倍。

框架文件 `src/sphero_env/` 一个字节未改，只是继承覆盖了一个公开方法。

## 11. 每一步的执行顺序

```text
1. 生成动作             scripted_action(travelled, initial_heading)
2. 仿真执行一步          sim_env.step(action)
3. 实机执行一步          robot_env.step(action)        （实机模式）
4. 取测量               extract_measurement(...)      → [heading, speed]
5. EKF 预测             ekf.predict(action)
6. EKF 更新             ekf.update(measurement)
7. 回写估计给两个环境     update_estimate(...)          （用于可视化与日志）
8. 记录一行提交数据       sim 真值 + EKF 估计 + P
9. 记录一行诊断数据       26 列原始传感器与滤波器内部量
10. 按实测位移推进轨迹     travelled += min(moved, 上限)
11. 等到下一个控制时刻     perf_counter 节拍
```

第 11 步用 `perf_counter` 而不是 `monotonic`：后者在本机分辨率是 15.625 ms，占一个控制周期的 16%，用它计时会把待测的抖动本身淹没掉。

仿真与实机**收到同一个动作**，但各自独立演化：仿真给出评分用的真值轨迹，实机提供测量。

## 12. CSV 输出与评分

写入采用「先写临时文件再原子替换」，中途失败不会把已有的有效提交截断成半个文件。写入前校验行数、列数、是否含 `NaN` 或无穷。

评分指标（阈值来自 `analyze_lab2.py` 的常量，代码直接引用而非重抄数字）：

| 指标 | 阈值 |
| --- | --- |
| 位置误差的平均平方马氏距离 | ≤ 4.0 |
| 卡方通过率（2 自由度，95% 门） | ≥ 0.90 |

马氏距离衡量的是「估计误差相对滤波器自称的不确定度有多大」：

```text
d² = (x_sim − x_est)ᵀ · P⁻¹ · (x_sim − x_est)
```

它同时惩罚两种错误——估计不准（分子大），以及协方差过于自信（分母小）。

`analyze_lab2.py` 还会画一张分析图：轨迹对比、95% 置信椭圆、逐步误差、NIS 序列。按作业说明的调参指引，NIS 图上同时画出卡方分布的**上下界**：超上界说明滤波器过于自信（应增大 `Q` 或 `R`），低于下界说明过于保守。

## 13. 诊断与标定工具

**`check_run.py`** —— 实机跑完后运行，读诊断日志逐项判断：

```bash
python labs/lab2/check_run.py
```

评分指标只说明滤波器是否自洽，**说不出它有没有真的在用传感器**。一次运行完全可能两项指标都通过，而速度「测量」仍是命令回显。这个脚本通过重放 `ImuHeadingSensor` 的算法、比对原始 yaw 与送进滤波器的值，直接回答这个问题；每项失败都附上具体的修改建议。

检查项：步数完整性、控制周期、速度是否来自编码器、航向是否来自 IMU、IMU 符号是否与配置一致、新息是否有系统性偏差、滤波器一致性。

**`calibrate_leg.py`** —— 实机标定：

```bash
python labs/lab2/calibrate_leg.py --target-leg 0.40
```

边长 = 速度 × 步数 × 周期，其中两个是机器人和蓝牙链路的属性而非可选项。脚本分两阶段：先在**零速静止**下测控制周期（周期是软件量，不占场地），再短距离直线测速度，最后给出目标边长对应的步数。

## 14. 安全与容错

- 仿真与实机环境都用 `try/finally` 包裹，异常时先 `emergency_stop()` 再关闭连接；
- Windows 蓝牙的已知瞬时失败重试 3 次、间隔 3 秒，连上之前不发任何运动命令；
- 实机运行的上下文在第 200 步后立即退出，先断开蓝牙再进入 `--hold` 的可视化保持；
- 诊断日志在**中止时也会写**——被迫停下的那次运行，恰恰是最值得看传感器轨迹的；这里的写入失败被有意吞掉，因为在 `finally` 中抛异常会顶替掉正在传播的真实异常（例如蓝牙断开），把真正的故障掩盖成磁盘错误。

## 18. 实现总结

```text
Lab 1 的运动模型（方程不变，常数按实机重标定）
+ 数值雅可比的 EKF（Joseph 形式协方差 + 特征值截断）
+ 真实传感器测量（编码器速度 + IMU 航向，均带丢帧回退）
+ 仿真与实机分设噪声矩阵
+ 沿黄线的圆角赛道轨迹，按实测位移推进，走满一圈即停
+ 蓝牙节流把控制周期从 209 ms 降到 105 ms
+ 26 列诊断日志与自动检查脚本
+ 68 项单元测试
```

贯穿整个实现的一条原则：**测量必须来自真正的传感器，模型必须描述真实的机器人**。滤波器的一致性指标可以靠调大协方差来「修好」，但那只是让滤波器承认自己不准；真正的改进来自把命令回显换成编码器、把假设的转向率换成陀螺仪实测、把时钟驱动的轨迹换成位移驱动的轨迹。
